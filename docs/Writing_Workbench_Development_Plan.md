# 글쓰기 작업실 개발 계획 · 18회차

> **이 파일은 처음 받은 계획의 합본 사본이다.** 기준 문서는 `docs/development/`이며, 이후 변경(계획 변경분 CH1~CH5, 회차별 스냅샷 규칙)은 그쪽과 `docs/development/PLAN_CHANGES.md`, 저장소 루트 `SNAPSHOTS.md`에만 반영한다.


**첫 목표는 06회에 실제 원고 한 편을 쓰고, 고치고, 되돌아보는 것이다.** 10회에는 회귀 구간 링크와 시점별 설정 조회, 14회에는 여러 창을 활용하는 장편 집필, 18회에는 Windows 설치·복구 검증까지 끝낸다.

‘회차’는 여기서 **AI에게 한 번에 맡길 개발 단위**다. 작품의 1화·2화와 구분한다. 예상 일수는 정하지 않았다. 각 회차의 통과 조건이 다음 작업의 출발점이다.

## 바로 시작하기

1. ZIP을 앱을 개발할 저장소 루트에 푼다. `docs/development/FOUNDATIONS.md`가 보이는 위치면 맞다. 기존 동명 문서가 있다면 그 내용을 먼저 보존하고 합친다. 이 단계에서 작가의 작품 폴더를 만들 필요는 없다.
2. 코딩 AI에서 **그 저장소**를 열고 아래 첫 지시를 붙여 넣는다. 저장소를 받지 못하는 채팅이라면 기초 설계·데이터 계약·품질 기준과 해당 회차 카드를 함께 전달한다. 실제 코드 접근·실행이 가능한 환경이어야 구현과 검증을 완료할 수 있다.
3. 회차가 끝나면 `docs/development/PROGRESS.md`에서 실제 결과와 증거를 확인한다. 다음 대화는 같은 저장소에서 해당 회차 파일 하나를 지정해 시작한다. 한 대화에서 가능한 범위를 넘으면 같은 회차의 미완료 항목부터 재개한다.

**첫 지시**

```text
이 저장소의 docs/development/sessions/01-foundation.md를 열고 이번 회차 작업 지시로 실행해줘.
프로젝트 규칙과 기초 설계를 확인하고, 구현·검증·PROGRESS.md 인계 기록까지 마쳐줘.
다음 회차는 시작하지 말고, 이번에 내가 직접 켜서 확인할 동작과 실제 테스트 결과를 알려줘.
```

**중단된 회차를 이어갈 때**

```text
docs/development/PROGRESS.md에서 진행중인 회차와 마지막 검증 결과를 확인해줘.
해당 sessions 파일의 완료 기준 중 남은 항목부터 이어서 구현하고, 완료 여부와 재현 방법을 기록해줘.
```

각 회차 카드 **전문**이 AI에게 줄 프롬프트다. 카드를 읽을 수 있는 코딩 AI에는 경로만 지정해도 된다. 공통 문서와 회차별 인수 조건은 나중에 작업자가 바뀌어도 유지한다.

# 로컬 글쓰기 작업실 · 기초 설계

## 이 앱에서 한 화를 쓰는 방법

작가는 작품 폴더를 한 번 지정한다. 앱 왼쪽에는 **회차 / 회차 요약 / 타임라인 / 세계관**이 보인다. ‘다음 화 쓰기’를 누르면 다음 번호의 실제 원고 파일이 먼저 생기고 기본 편집기에서 열린다. 최초 기본값은 VS Code다. 내장 편집기나 메모장도 선택할 수 있다. 작가는 집필 도중 언제든 저장하고, 초고 완성·퇴고 완료처럼 남기고 싶은 순간에 ‘회차 커밋’을 누른다. 어떤 두 커밋도 비교할 수 있다.

351화를 쓰는 동안 보조 모니터에는 300~350화 회귀 타임라인을 고정하고 다른 창에는 현재 회차까지의 주인공 능력을 띄운다. 352화로 넘어가면 능력 창은 따라가고 회귀 구간은 제자리에 남는다. 나중에 327화에 사건 하나를 추가하면 회귀 구간 링크를 다시 열었을 때 그 사건이 보인다. 327화를 퇴고하면 거기에 근거한 요약·사건·인용에 ‘재확인’이 붙는다.

## 화면과 조작

- **왼쪽**에는 네 개의 고정 루트와 실제 문서가 있다. 접힘·선택·스크롤을 보존한다. 아직 자료가 없으면 루트에서 바로 첫 문서나 타임라인을 만든다. 세계관 하위 폴더와 태그는 별개다.
- **가운데**는 집필·요약·타임라인·설정·이력 중 열린 문서다. 상단에서 현재 작품, 회차, 저장 상태를 확인한다. 저장 중, 저장됨, 외부 변경, 충돌, 읽기 전용, 실패를 구분하고 실패 시 다시 시도할 수 있다.
- **참고창**은 ‘현재 회차 따라가기 / 현재 대상 고정’ 중 하나다. 임의로 띄운 인물 카드나 회귀 범위는 기본 고정, ‘직전 화’나 ‘현재 능력’ 바로가기는 기본 따라가기다. 무거운 본문 편집기는 편집 창에서만 올린다.
- **탐색**은 Ctrl+P로 문서·구간 바로 열기, Ctrl+Shift+F로 작품 전체 검색. 검색 결과에서 해당 문장으로 갔다가 뒤로 가면 검색어·범위·스크롤이 남는다. 창 복제·필터 변경은 작품 데이터 편집과 독립이다.
- **소유권**은 현재 원고는 작가, 확정본은 회차 커밋, 파생 검색 자료는 앱에 있다. AI 생성 요약을 전제하지 않는다. 작가가 직접 쓴 요약도 원고와 같은 수준으로 보존한다.

## 개발 문서와 작품 폴더

이 패키지의 `docs/development/`는 **앱 소스 저장소**에 둔다. 작가가 선택하는 **작품 폴더**의 규격은 같은 디렉터리의 `WORKSPACE_FORMAT.md`에 있다. 개발 문서가 작품 트리에 나타나지 않도록 한다. 기존 프로젝트에서는 같은 역할의 모듈과 명령을 재사용하며 도구 버전은 실제 검증 후 잠금 파일에 남긴다.

## 완료 단위

- 06회 종료 시 원고 한 편을 생성·외부 집필·퇴고·비교한다.
- 10회 종료 시 3화짜리 작품에서 사건·설정·과거 구간을 관리한다.
- 14회 종료 시 여러 창을 열어 장편의 실제 내용을 찾고 대조한다.
- 18회 종료 시 깨끗한 Windows 사용자 환경에 설치하고 1,000화 규모에서 다시 연다.

첫 버전 범위는 개인 로컬 집필이다. 계정, 공동 실시간 편집, 클라우드 동기화, 온라인 AI 호출, 출판용 조판은 별도 제품 결정으로 남긴다. 빌드 시간표와 측정 수치는 실측 후 기록한다.

## 확인할 공식 자료

기술 동작의 근거와 이 프로젝트의 설계 목표를 구분한다. 아래 자료는 구현 AI가 해당 기능에 착수할 때 대조할 출발점이다.

- Rust 코어와 여러 WebView의 역할. [Tauri process model](https://v2.tauri.app/concept/process-model/)
- 로컬 본문 색인과 trigram의 3글자 미만 전문 검색 제약. [SQLite FTS5](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)
- 작품 폴더·원고 파일·행 위치를 외부 에디터로 여는 옵션. [VS Code CLI](https://code.visualstudio.com/docs/configure/command-line)
- 오프라인 한국어 철자 후보의 데이터·배포 조건 검토용 저장소. [Korean dictionary for Hunspell](https://github.com/spellcheck-ko/hunspell-dict-ko)

## 쓰기와 복구

1. 작업 원고와 확정 커밋은 별도다. 작업 저장은 파일을 갱신하고 회차 커밋만 이력을 늘린다. 외부 편집 직후 커밋하면 앱은 디스크 내용을 다시 읽는다. 앱에 다른 초안이 동시에 있으면 충돌을 먼저 해결한다.
2. 앱 내부의 문서 변경은 작품/문서 단위 쓰기 소유자를 통해 직렬화한다. 편집 창은 읽은 시점의 지문과 요청 ID를 보낸다. Rust가 쓰기 직전 상태를 확인하고 불일치면 양쪽 내용을 보존한다. 같은 요청 ID로 다시 시도해도 회차·커밋이 중복 생성되지 않는다.
3. 본문 한 개는 같은 볼륨의 임시 파일에 쓴 뒤 대상 OS에서 검증한 교체 방식으로 게시한다. 여러 파일로 된 회차·커밋은 임시 디렉터리에서 완성 후 한 번에 게시하는 방법을 우선한다. 영구 객체의 가시성·실패 시 복구 규칙을 정하고 실제 중단 지점에 실패를 주입한다. 임의의 외부 편집기와 경합하는 최후의 순간까지 OS가 보장한다고 가정하지 않는다. 관측한 외부 버전과 미저장 초안의 복구 사본을 보존한다.
4. 재시작하면 미완성 기록과 남은 초안을 검사한다. 작가에게 양쪽 사본을 표시하고 선택 전까지 복구 원본을 보존한다. 잠긴 파일, 권한 부족, 용량 부족 시 ‘저장됨’을 표시하지 않는다. 처음 여는 작품은 쓰기 전에 형식과 버전을 확인하고 모르는 상위 버전은 원본을 보존하며 안내한다.
5. 인앱 쓰기는 UTF-8을 사용한다. 외부에서 연 UTF-8 BOM·CRLF 파일은 가능한 한 기존 형식을 유지한다. 읽기 실패·지원하지 않는 인코딩은 원문 바이트를 보존하고 설명한다. 검색용 정규화는 복사본에서만 한다.
6. SQLite 및 기기별 창 배치·최근 작품 경로는 앱 사용자 데이터에 분리한다. 작품 원본은 위 폴더만으로 다른 PC에서 복원된다. 작품 복사본을 원본과 섞지 않도록 캐시·세션 식별에 실제 경로도 포함한다. 감지하지 못한 외부 변경은 앱 시작·전면 복귀·수동 새로고침에서 재대조한다.
7. 한 작품을 두 프로세스에서 열면 쓰기 소유권은 하나다. 두 번째는 기존 프로세스로 전달하거나 읽기 전용으로 연다. 앱 내부 보조 창은 같은 코어를 공유한다. 경로를 벗어나는 링크·접합점은 쓰기 전에 검사하고, 사용자가 고른 기존 폴더의 무관한 파일은 보존한다.

## 회차 간 추가 계약

- 복선의 현재 status는 표시용 파생값이다. 등장·회수·재개는 불변 transitionId, 공개 회차, 회차 내 순서, 선택적 장면 링크를 지닌 이력으로 보존한다. 7화 등장 → 32화 회수 → 40화 재개라면 25/35/41화 기준 상태는 각각 미회수/회수/미회수다.
- 인용 위치는 문서 ID와 어느 텍스트 버전을 읽었는지 함께 기록한다. UI·Rust·SQLite에서 쓰는 바이트/문자/UTF-16 단위가 다를 수 있으므로 변환 경계에서 같은 본문으로 왕복 검증한다. 원문으로 되돌아갈 수 없는 검색 정규화 오프셋을 직접 적용하지 않는다.
- `timelines/collections/`는 이름 있는 타임라인, `timelines/views/`는 타임라인을 조회하는 저장 조건이다. 작가가 사건을 숨기면 보기 조건만 바뀐다. 사건을 한 타임라인에서 떼면 소속 관계만 바뀐다. 사건 자체 삭제는 남은 소속과 링크 영향을 확인한 명시적 동작이다.
- `dictionary/words.json`은 16회부터 사용하는 작품별 사용자 사전이다. 빈 폴더는 첫 사용 시 만들 수 있다. 새 필드는 기본값을 정의해 02~15회의 작품도 그대로 연다. `workspace.json`의 schemaVersion과 개별 데이터 변환 정책을 함께 기록한다.
- `독자 기준`에 들어가는 구조화된 사실은 공개 회차로 선별한다. 자료 전체에 공개 범위를 줄 수 없는 자유 메모는 기본 제외한다. 사용자가 직접 작성한 요약 안의 의미상 스포일러를 자동 검출한다고 보장하지 않는다. AI 자료 미리보기에서 문서별 제외가 가능해야 한다.

## 17회에서 실제로 잴 예산

미달은 관측 조건·느린 구간·수정 전후 결과를 남긴다. 데이터 손실, 무음 덮어쓰기, 사라진 커밋, 독자 기준 미래 누출은 출시 차단이다. 숫자 목표 미달은 영향과 실측을 공개해 출시 여부를 판단하며 임계치를 뒤에서 바꾸지 않는다.

# 01회 · 실행 뼈대와 첫 작업 화면

**작가가 얻는 결과** · 앱을 켜면 네 개의 루트와 언어 전환을 볼 수 있다.

이 문서 전체를 이번 회차의 구현 지시로 사용해라. 저장소의 기존 규칙과 `docs/development/FOUNDATIONS.md`, `WORKSPACE_FORMAT.md`, `QUALITY_GATES.md`, `PROGRESS.md`를 확인하고 실제 코드 상태와 대조해라. 네 공통 문서는 모두 `docs/development/` 아래에 있다. 이미 구현한 부분은 동작을 검증해 재사용하고 이번 범위의 코드 수정, 테스트, 인계까지 수행해라.

**시작 조건** · 기능이 통합된 16회 빌드와 QUALITY_GATES.md가 있다.

### 구현 순서

1. 고정 시드로 가상 소설 1,000화 × 약 5,000자, 사건 10,000개, 화당 과거판 3개를 생성한다. 표본에는 자주/드물게 나오는 한글 한두 글자, 여러 회차로 나뉜 같은 이름, 동일 인용, 회귀, 미정 시간, 동률 좌표가 섞여야 한다. 검색 정답을 생성기에서 독립적으로 확인한다.
2. release 빌드, 장비·OS·RAM·SSD·버전·시드·데이터 크기를 기록한다. 첫 색인/웜 재시작, 빠른 열기/일반/짧은 검색, 취소, 입력 지연, 1창과 4창 총 메모리·증가량, 과거판 포함 검색을 같은 조건에서 측정한다.
3. 느린 경로 한 개씩 프로파일링해 원인을 잡는다. 우선 전 자료 재읽기·중복 색인·전문 DOM 렌더링·모든 창의 에디터 인스턴스를 확인한다. 데이터 정확도·입력 보존을 재측정하고 전후 수치를 원본 보고서에 남긴다.
4. 중간 종료·캐시 삭제·작품 이동 후 다시 표본을 열고 원본/이력 해시, 관계 ID, 기대 검색 결과가 같은지 검사한다. 실측 자료와 재현 명령을 docs/development/benchmarks/에 남긴다.

### 완료 기준

# 18회 · 설치·이전 작품 복구·1.0 판정

**작가가 얻는 결과** · 새 Windows 사용자 환경에서 설치하고 작품 폴더 하나로 원고·자료·이력을 되살린다.

## AI 작업 지시

이 문서 전체를 이번 회차의 구현 지시로 사용해라. 저장소의 기존 규칙과 `docs/development/FOUNDATIONS.md`, `WORKSPACE_FORMAT.md`, `QUALITY_GATES.md`, `PROGRESS.md`를 확인하고 실제 코드 상태와 대조해라. 네 공통 문서는 모두 `docs/development/` 아래에 있다. 이미 구현한 부분은 동작을 검증해 재사용하고 이번 범위의 코드 수정, 테스트, 인계까지 수행해라.

**시작 조건** · 17회 실측 보고서와 이전 회차의 미확인 항목을 검토한다.

### 구현 순서

1. 첫 배포 대상 Windows x64용 설치 파일을 만든다. 버전·빌드 명령·WebView/사전 의존성·설치 경로·배포 표기·체크섬을 기록한다. 개발 도구가 없는 계정/기기에서 실행하고 VS Code 유무 두 경로를 확인한다. 설치 시 필요한 네트워크와 설치 후 오프라인 집필을 구분한다.
2. 초기 버전 형식의 작은 고정 작품과 장편 작품을 복사해 연다. 작품 버전 업그레이드가 실제로 필요한 경우 사전 백업·중단 후 복구를 시험하고, 형식 변경이 없으면 동일 버전 재개와 상위 버전 읽기 보호를 시험한다. 사용 중인 실제 작가 작품은 테스트 데이터로 쓰지 않는다.
3. Q1~Q11과 각 회차의 보류 항목을 원래 사용자 흐름에서 다시 수행한다. 실제 설치 여부, 실제 한글 IME/교정, 외부 편집기, 모니터 분리, 오프라인 실행을 점검한다. 테스트 불가 항목은 재현 명령·필요 환경과 함께 남긴다.
4. 짧은 작가용 시작 안내를 작성한다. 작품 생성, 기본 편집기, 첫 커밋·비교, 첫 타임라인, 구간 링크, 백업/복구, 언어 전환을 설명한다. AI가 확보한 설치 파일과 보고서까지 만들고 공개 배포는 별도 사용자 요청으로 둔다.

### 완료 기준

- [ ] **S18.A** · 새 사용자에서 설치 → 1화 작성 → 2회 커밋 → 사건·설정 연결 → 보조 창 띄우기 → 종료·재실행이 가능하다.
- [ ] **S18.B** · 작품 폴더만 새 위치로 복사해 새 캐시로 열어도 본문·요약·커밋·링크·태그·사전·범위 뷰를 복원한다. 재설치·제거가 작품 파일을 삭제하지 않는다.
- [ ] **S18.C** · 차단 결함·미확인 필수 경로가 있으면 ‘출시 보류’로, 증거가 모였으면 ‘1.0 후보 통과’로 기록한다. 성능 목표 미달은 17회 결과를 인용해 별도로 판정한다.
